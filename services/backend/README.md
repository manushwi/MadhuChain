# MadhuChain Backend

The single bridge between MadhuChain apps and the Hyperledger Fabric ledger.
REST API (Express) + chronicle DB (Prisma/TimescaleDB) + Fabric Gateway (`@hyperledger/fabric-gateway`), written in TypeScript and run with [Bun](https://bun.sh).

Every madhu-chain write (`mint`, `RecordReceived`, quality tests, processing,
packaging, blend, transfer, clear-flag) is submitted as a Fabric transaction to
`madhuchain-cc` on `madhuchain-channel`; responses are mirrored into Postgres for
querying. The `GET /api/verify/:jarId` endpoint resolves a jar back to its on-chain
origin and quality history.

## Prerequisites

- Node 20+ or [Bun](https://bun.sh) (dev server runs on Bun; TS is type-checked with `tsc`)
- A running Fabric test network with `madhuchain-channel` and `madhuchain-cc` deployed,
  and identities enrolled. See `chain/network/enrollIdentities.sh` and the chain README.
- TimescaleDB/Postgres reachable at `DATABASE_URL`.

## Setup

```bash
cp .env.example .env        # fill in secrets + Fabric paths
bun install                 # or: npm install
bun run db:migrate          # apply Prisma migrations
bun run db:seed             # seed hives + demo user (amara@madhuchain.app / madhuchain123)
bun run dev                 # starts API on :4000 (bun --watch)
```

Type-check / tests:

```bash
bun run build               # tsc --noEmit equivalent via tsconfig
bun test                    # bun test
```

## Fabric connectivity

Connection settings live in `.env` (see `.env.example`):

| Var | Meaning |
| --- | --- |
| `FABRIC_CONNECTION_PROFILE` | org1 `connection-org1.json` (paths relative to `services/backend`) |
| `FABRIC_MSP_ID` | `Org1MSP` |
| `FABRIC_IDENTITY_DIR` | default read identity; write transactions select sibling role identities generated by `enrollIdentities.sh` |
| `FABRIC_PEER_ENDPOINT` | `localhost:7051` |
| `FABRIC_PEER_HOST_ALIAS` | `peer0.org1.example.com` — used as `grpc.ssl_target_name_override`/`grpc.default_authority` because the name only resolves inside Docker |
| `FABRIC_ORDERER_ENDPOINT` | `localhost:7050` |

Notes on this setup (Windows/Git Bash):

- All `chain/...` paths in `.env` are relative to `services/backend` (cwd), i.e. `../../chain/...`.
- The Fabric hostname is dialed as `localhost:7051` while TLS SNI keeps the on-chain identity
  `peer0.org1.example.com` — see `src/services/fabric/fabricService.ts`.
- Identity signing is custodial. The backend selects the enrolled Beekeeper, Transporter,
  LabTech, FactoryWorker, QCManager, or Distributor identity matching the authenticated JWT
  role. Admin does not bypass chaincode authorization.
- Public signup only provisions Consumer or Beekeeper users. Other operational roles must be
  provisioned administratively.

## API

Auth: `POST /api/auth/login` returns a JWT; pass it as `Authorization: Bearer <token>`.
Only `/health`, `/api/auth/login` and `/api/auth/signup` are public.

### Hives & sensors

| Method | Path | Body / notes |
| --- | --- | --- |
| GET | `/api/hives` | list hives |
| POST | `/api/hives` | create hive |
| GET | `/api/hives/:id/live` | latest live readings |
| GET | `/api/hives/:id/readings` | historical readings |
| POST | `/api/sensor-data` | ingest sensor readings (device API key) |

### Fabric madhu-chain (core flow)

| Method | Path | Body (zod) |
| --- | --- | --- |
| POST | `/api/batches/mint` | `{ hive_ids[], harvest_start, harvest_end, weight_kg }` → returns `batch_id`, `lot_id`, PDF barcode |
| POST | `/api/batches/:id/received` | `{ transporter_id, weight_in }` |
| POST | `/api/batches/:id/quality-test` | `{ stage: INTAKE\|OUTPUT\|FINAL, moisture, hmf, diastase, sugar_profile{fructose,glucose,sucrose}, isotope_ratio }` |
| POST | `/api/batches/:id/processing-action` | `{ action_type, parameters?, equipment_id, weight_before, weight_after, parent_lots? }` |
| POST | `/api/batches/:id/packaging` | `{ jar_count, average_jar_weight_kg }` (must reconcile with output weight within 2%) |
| POST | `/api/batches/:id/blend` | `{ sources[{lot_id, weight_kg}].min(2), weight_kg }` (mass balance within 2%) — creates the next `BATCH-###` |
| POST | `/api/batches/:id/transfer` | `{ to_identity }` |
| POST | `/api/batches/:id/clear-flag` | `{ resolution: CLEARED\|REJECTED }` (QC Manager) |
| GET | `/api/batches` · `/api/batches/:id` | list / detail (DB mirror) |
| GET | `/api/batches/:id/barcode` | on-chain barcode PDF for a batch |
| GET | `/api/verify/:jarId` | **ledger truth**: resolves jar → batch, returns origin (beekeeper, harvest window) + all quality tests |
| POST | `/api/verify/:jarId/appearance-report` · `/api/verify/:jarId/review` | consumer appearance reports / reviews |

### Operational

`GET /api/alerts`, `POST /api/alerts/:id/ack`, `GET /api/profile`.

### End-to-end example (curl)

Each lifecycle request below must use a token for its required role. A single Beekeeper token
can no longer execute transporter, lab, factory, or QC operations.

```bash
TOKEN=$(curl -s -X POST localhost:4000/api/auth/login -H 'Content-Type: application/json' \
  -d '{"email":"amara@madhuchain.app","password":"madhuchain123"}' | jq -r .token)
AUTH="Authorization: Bearer $TOKEN"

curl -s -X POST localhost:4000/api/batches/mint -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"hive_ids":["H-001"],"harvest_start":"2026-08-20T00:00:00.000Z","harvest_end":"2026-08-22T00:00:00.000Z","weight_kg":100}'  # -> BATCH-001 / HC-LOT-001
curl -s -X POST localhost:4000/api/batches/BATCH-001/received -H "$AUTH" -H 'Content-Type: application/json' -d '{"transporter_id":"T-1","weight_in":100}'
curl -s -X POST localhost:4000/api/batches/BATCH-001/quality-test -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"stage":"INTAKE","moisture":17.2,"hmf":30,"diastase":12,"sugar_profile":{"fructose":38,"glucose":34,"sucrose":2},"isotope_ratio":-24.5}'
curl -s -X POST localhost:4000/api/batches/BATCH-001/processing-action -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"action_type":"heating","weight_before":100,"weight_after":97.4}'
curl -s -X POST localhost:4000/api/batches/BATCH-001/quality-test -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"stage":"OUTPUT","moisture":17.0,"hmf":28,"diastase":13,"sugar_profile":{"fructose":38,"glucose":34,"sucrose":2},"isotope_ratio":-24.5}'
curl -s -X POST localhost:4000/api/batches/BATCH-001/packaging -H "$AUTH" -H 'Content-Type: application/json' -d '{"jar_count":240,"average_jar_weight_kg":0.4}'
curl -s -X POST localhost:4000/api/batches/BATCH-001/quality-test -H "$AUTH" -H 'Content-Type: application/json' \
  -d '{"stage":"FINAL","moisture":17.0,"hmf":27,"diastase":14,"sugar_profile":{"fructose":38,"glucose":34,"sucrose":2},"isotope_ratio":-24.4}'
curl -s localhost:4000/api/verify/BATCH-001-JAR-0001 -H "$AUTH"
```

Chain state flow: `RECEIVED → INTAKE_TEST → PROCESSING → OUTPUT_TEST → PACKAGING → FINAL_QC → RELEASED`, with `FLAGGED` set when fraud/QC checks trip (compositional drift, mass-balance mismatch, jar-weight reconciliation). A `clear-flag` with `CLEARED` resumes at `PROCESSING`.

### End-to-end smoke test

`scripts/e2e-chain.sh` drives the entire lifecycle into the ledger through the REST
API — mint → received → intake → processing → deliberately-bad output test (asserts
`flagged=true`) → QC clear → output → packaging → final → `RELEASED`, then consumer
verify of a jar and a mass-balanced blend — and fails the script on any assertion
mismatch.

```bash
PATH="$PWD/../../chain/network/fabric-samples/bin:$PATH" bash scripts/e2e-chain.sh
```

Requires a running backend + Fabric network + seeded DB (see Setup).

## Layout

- `src/routes/` – REST handlers (auth, hives, sensorData, batches, factory, verify, alerts, profile)
- `src/services/fabric/fabricService.ts` – Fabric Gateway client (submit/evaluate)
- `src/services/fraudChecks.ts` – pre-flight QC/fraud validations
- `src/db/` – Prisma client
- `prisma/` – schema + migrations + seed
